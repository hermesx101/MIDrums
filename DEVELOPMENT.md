# Developing MI Drums

This guide contains the day-to-day workflow. See [ARCHITECTURE.md](ARCHITECTURE.md) for module ownership and data flow.

## Environment

Install a current stable Rust toolchain using [rustup](https://rustup.rs/) or an equivalent distribution. The workspace uses Rust 2021 and Cargo resolver 2; no minimum compiler version is declared in the repository.

The desktop application also needs the platform libraries required by:

- `eframe` for the native window and rendering
- `midir` for MIDI input
- `rodio` for audio output/decoding
- `rfd` for native file dialogs

The current validated development environment is Windows. On Linux or another Unix-like system, install the appropriate MIDI/audio/window-system development packages for that distribution. Those platform combinations have not yet completed project validation.

## Common commands

Run the app:

```sh
cargo run -p drums-app
```

Compile the workspace without running:

```sh
cargo build --workspace
```

Build the optimized app:

```sh
cargo build --release -p drums-app
```

Run the tests:

```sh
cargo test --workspace --no-fail-fast
```

Run the complete local quality gate:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace --no-fail-fast
```

Apply Rustfmt when formatting needs correction:

```sh
cargo fmt --all
```

`Cargo.lock` is committed because the workspace produces a desktop application. Do not remove it from version control.

## MIDI debugging

1. Open Settings -> MIDI Monitor.
2. Refresh devices and connect the intended MIDI input.
3. Inspect message kind, note/controller number, velocity/value, channel, and timestamp.
4. For a pad that produces unexpected behavior, record every event generated by one physical action, including Note Off and CC messages.
5. Compare the input identity with Settings -> Drum Mapping.

The Monitor displays parser output before drum mapping or scoring. It is therefore the right first boundary for separating hardware/driver output from mapping or practice behavior.

For the NUX DM-1 pedal investigation, capture at least:

- pedal down and pedal up without striking the hi-hat
- closed and open hi-hat strikes
- a discrete foot-chick, if the module emits one
- controller number, value range, channel, event order, and timestamps

Do not assume multiple events from one action are a software defect until the raw monitor trace is understood.

## Mapping and persistence debugging

Mappings are associated with the exact MIDI device name. If a device appears under a different operating-system name, it receives a different mapping file.

Two environment overrides are available for isolated testing:

- `DRUMS_CONFIG_DIR` changes the mapping directory.
- `DRUMS_HISTORY_PATH` changes the completed-session history file.

Use temporary paths for manual destructive-data tests. Preferences and Track Library persistence do not currently expose equivalent environment overrides.

Application data is TOML. A malformed per-device mapping is rejected by the direct load path; `load_all` skips invalid mapping files. A malformed session history returns an error rather than being silently discarded. Practice settings and Track Library loading currently fall back to defaults/empty data on read or parse failure.

## Audio debugging

The MIDI transport is authoritative. Backing audio is sought to a position derived from transport time and the configured Audio Sync Offset. MIDI Input Latency compensates the live hit timestamp separately and does not change the scoring tolerance.

When validating audio:

1. Start with both offsets at zero.
2. Verify play, pause, stop, seek, count-in completion, and loop wrap.
3. Adjust MIDI latency and audio sync independently.
4. Repeat with the target audio device and release build, because driver/buffer behavior may differ from development hardware.

Backing audio accepted by the file picker includes MP3, WAV, OGG, and FLAC. Decoder/backend availability still depends on the platform audio stack and file contents.

## Project conventions

- Keep hardware-independent behavior in `drums-core`; keep egui, dialogs, and audio-device ownership in `drums-app`.
- Preserve raw MIDI timestamps and musical ticks. Do not derive scoring time from frame count.
- Resolve physical input through `ObservedMidiInput` and `DrumKitConfiguration`; do not compare live raw note numbers directly with lesson note numbers.
- Treat Note On velocity zero as Note Off.
- Keep continuous pedal CC state separate from playable Note hits unless the product/scoring model is deliberately extended.
- Preserve aliases: one logical drum may own multiple physical input identities.
- Make conflicts explicit; do not silently move an input between logical drums.
- Progress and Performance Analysis must derive from the authoritative completed-session history.
- Never delete source MIDI/audio files when changing library or reset behavior.
- Add focused tests for domain changes and run the complete quality gate before handoff.

## Release preparation

Before publishing a release:

1. Complete the required hardware/manual work in [PROJECT_STATUS.md](PROJECT_STATUS.md).
2. Run the quality gate from a clean checkout.
3. Build with `cargo build --release -p drums-app`.
4. Smoke-test the produced binary on a clean machine for each supported platform.
5. Add the license text files required by the Cargo `MIT OR Apache-2.0` declaration.
6. Document the supported operating systems and distribute only artifacts that were tested there.

The repository does not currently define CI, an installer, signing, or release automation.
